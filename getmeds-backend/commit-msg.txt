gate medrep orders behind management approval; add per-order division/salesperson overrides

Management approval gate (see claude/2026-09-07-management-approval-gate.md):
"When medrep creates an order, the order will not sync to zoho unless the
management checks it." A MedRep's own order submission now stops at a new
pending_management_approval status instead of reaching Zoho immediately —
both entry points (create()'s single-call submit, which is what the UI
actually uses, and submit()'s own gate) land there. Management/admin get
three explicit outcomes, mirroring finance.controller.js's verifyAccount
pattern: approve() (logs MANAGEMENT_APPROVED, then runs the same
syncOrderToZohoAndFinalize() pipeline submit() always ran), reject() (reason
required, -> on_hold, never touches Zoho), and sendBack() (reason required,
-> draft, so the MedRep or Management can fix it via the new updateDetails()
endpoint and resubmit through the same gate). An order Management/admin
raises themselves is unaffected and still goes straight through.

New: workflow/stateMachine.js (pending_management_approval + its edges),
orders.routes.js (approve/reject/send-back/details routes),
pages/management/ApprovalQueuePage.jsx (Approve/Send Back/Reject queue,
routed at /management/approvals), a sidebar entry, an OrderStatusBadge
style, and an Order Details / Management Approval / Submit Order panel on
OrderDetailPage.jsx for acting on a single order directly.

The alternative considered and rejected: gating only inside submit(). That
was the first version built, and it didn't work — every real order actually
goes through create() in one call (OrderForm.jsx never calls a separate
submit()), so submit()'s gate was dead code. Fixed by adding the identical
isMedRepDirectSubmit check to create() itself; see the doc's "Bug in the
first version" section for the full investigation.

Per-order Division/Sub-division/Salesperson overrides (see
claude/2026-09-05-divisions-enum.md): three new orders columns
(sub_division, division, salesperson) so a Management-raised order can
carry its own values instead of only ever inheriting the ordering MedRep's
account — needed because a Management account typically has no Division of
its own. sub_division is editable by whoever raises the order (MedRep or
Management); division/salesperson are Management-only, since a MedRep's
own account still drives theirs and also determines their Salesperson.
division is checked against the same 15-entry DIVISIONS list Sign
Up/Profile Settings use; salesperson is checked live against Zoho's own
Salesperson list, since Zoho is what actually rejects an unrecognized name
(same reasoning as the Sep 2 incident already in working-agreements.md).
OrderForm.jsx gains editable fields for both plus a read-only "Admin" pill
showing who actually created the order; NewOrderPage.jsx's Salesperson
pre-check banner is now MedRep-only, since a Management account's own
generated salesperson string was never going to be submitted and the
banner was warning about a value that didn't matter.

Backfill Zoho field edits outside the live webhook (see the same doc, "Sep
7 (5)"): zohoReconcileService.js's reconcileOrder() — the shared function
behind "Sync from Zoho", the page-open refresh, and the background poller
— never ran the existing zohoEditDiffService field-diff that
webhook.controller.js's salesorder.edited branch already does, so a field
edited directly in Zoho only ever reflected here if the live webhook
happened to reach the app at that exact moment. It now runs the same diff
unconditionally and logs a ZOHO_SO_EDITED event when something changed,
closing that gap for the six tracked fields.

Also removes commit-msg.txt, a leftover scratch file from an earlier
commit that was never cleaned up.

No automated tests were added for any of this (tracked as outstanding in
the approval-gate doc); the existing suite is unchanged. End-to-end
verification is still outstanding per that doc's own test checklist —
run it before treating this as done.
